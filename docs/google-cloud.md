# Google Cloud в GitMir

## Что интегрировано

GitMir получает отдельный навык `$google-cloud`, запись Google Cloud в существующем каталоге навыков панели и исполняемую диагностику на Node.js. Это интеграция для **проектов, которыми управляет GitMir**, а не перенос самой панели в Google Cloud.

Диагностика читает версию SDK и локальный контекст `gcloud`, связывает локальный репозиторий с явно указанным GCP project ID и по отдельному флагу проверяет чтение метаданных этого проекта. Навык передаёт дальнейшую облачную работу в существующие `$task-planner`, `$task-runner` и модель GitMir.

Windows-рецепт исправления WinGet `Unknown` теперь имеет определённое место: **обслуживание локального инструментария этой интеграции**. Он не является этапом запуска GitMir и не выполняется автоматически.

## Установка и точки входа

Требования проекта остаются прежними: Node.js 22.18+; для диагностики нужен установленный `gcloud`. На Windows используется системный Windows PowerShell для запуска `gcloud.cmd`. Дополнительных runtime-зависимостей npm нет. Права администратора для обычной диагностики не нужны; не запускайте её под другой учётной записью без необходимости.

После получения ветки с интеграцией выполните существующий `install.ps1` на Windows или `install.sh` на macOS/Linux и перезапустите Codex. Установщики связывают целые каталоги навыков, поэтому вспомогательные скрипты устанавливаются вместе с `SKILL.md`. В Codex:

```text
$google-cloud Проверь локальный SDK и контекст этого проекта. Ничего в облаке не меняй.
```

В панели GitMir используйте запись **Google Cloud** в существующем каталоге навыков. Это обычный навык панели, а не новая вкладка с live-метриками, OAuth-окно или облачный API на сервере GitMir. Backend и frontend панели не переписаны.

Из каталога GitMir доступна команда:

```powershell
npm run gcloud:doctor -- --directory "C:\Projects\my-app"
```

На macOS/Linux та же команда принимает POSIX-путь:

```bash
npm run gcloud:doctor -- --directory "/home/user/projects/my-app"
```

`--directory` указывает именно на **управляемый проект**. По умолчанию используется текущий рабочий каталог процесса; при `npm run` это обычно корень GitMir. Несуществующий каталог считается ошибкой, а не новым пустым проектом.

## Привязка проекта

В каталоге управляемого проекта создайте `.gitmir/google-cloud.json` с подтверждёнными значениями. Полный пример формата:

```json
{
  "projectId": "demo-project-123",
  "region": "europe-west1"
}
```

Это демонстрационные значения, не идентификаторы пользователя. `projectId` обязателен при наличии файла, `region` необязателен. Разрешены только эти поля; неизвестные поля отвергаются. Поддерживаются стандартные project ID длиной 6–30 символов из строчных латинских букв, цифр и дефисов. Числовые project numbers и старые domain-scoped IDs здесь не поддерживаются.

Файл ограничен 16 KiB и должен содержать JSON. UTF-8 BOM поддерживается. `region` проходит только проверку формата: доступность региона для конкретной службы не проверяется, глобальная команда `projects describe` его не использует.

Без файла возможна локальная диагностика. Проверка Cloud API без явной привязки запрещена: случайный активный проект в `gcloud` не становится целью. Диагностика сама файл не создаёт и не меняет.

Токены, OAuth client secrets, JSON-ключи service accounts, пароли и содержимое ADC в этот файл не помещаются. Сам project ID также может быть внутренней информацией: решение о коммите привязки остаётся за владельцем проекта.

## Режимы запуска

Локальная диагностика в человекочитаемом виде:

```powershell
npm run gcloud:doctor -- --directory "C:\Projects\my-app"
```

Чистый JSON без служебного вывода npm:

```powershell
node plugin/skills/google-cloud/scripts/doctor.mjs --directory "C:\Projects\my-app" --json
```

Явная проверка доступа к привязанному проекту через Google Cloud API:

```powershell
npm run gcloud:doctor -- --directory "C:\Projects\my-app" --verify-project --json
```

Справка:

```powershell
npm run gcloud:doctor -- --help
```

Обычный запуск выполняет только три команды чтения локального контекста: `gcloud version`, `gcloud config list` и `gcloud auth list`. Две последние команды возвращают свойства активной конфигурации и сведения о сохранённых аккаунтах, а не доказательство актуальности credentials.[1][2]

`--verify-project` добавляет `gcloud projects describe` с project ID одновременно в позиционном аргументе и `--project`. Команда запрашивает метаданные конкретного проекта и может завершиться ошибкой из-за отсутствия проекта или прав.[3] Глобальная конфигурация CLI при этом не меняется. Используются текущая конфигурация аутентификации, environment overrides и настроенная impersonation; это не изолированный вход в другой аккаунт.

## Значение результата

| Статус | Что доказано | Что не доказано |
|---|---|---|
| `local-only` | SDK ответил, локальные команды отработали и выдали ожидаемую структуру | Доступ к Cloud API, ADC, биллинг, права деплоя |
| `verified-project-read` | Метаданные именно привязанного проекта прочитаны; lifecycleState — ACTIVE | Права на Cloud Run, IAM, Artifact Registry, Google Ads API, квоты и биллинг |
| `blocked` | Один из этапов не завершён успешно | Любая готовность, зависящая от этого этапа |

Коды завершения: **0** — запрошенные проверки выполнены; **1** — ошибка проверки; **2** — ошибка аргументов или привязки. Код 0 в локальном режиме не означает «облако готово к деплою». Поле `cloudAccessVerified` относится только к чтению метаданных проекта.

В отчёт попадают версия SDK, project binding, выбранный аккаунт и проект CLI, настроенная impersonation, количество локальных аккаунтов, предупреждения и код ошибки этапа. Сырые JSON-ответы CLI и stderr в отчёт не копируются. Тем не менее email аккаунта и project ID нельзя считать автоматически пригодными к публичной публикации. Отчёты не записываются в проект и не коммитятся автоматически.

ADC всегда помечается как `not-checked`. Аутентификация `gcloud` и Application Default Credentials — разные конфигурации: успешный вход в CLI не доказывает работу SDK приложения, а отсутствие локального аккаунта CLI не доказывает отсутствие ADC или workload identity.[4]

## Ошибки и диагностика

`GCLOUD_NOT_FOUND`: `gcloud` не найден в PATH процесса; на Windows проверьте наличие `gcloud.cmd` и системного Windows PowerShell. Перезапустите терминал после изменения PATH. Не подменяйте отсутствующий CLI скачанным из случайного источника скриптом.

`GCLOUD_COMMAND_FAILED`: команда завершилась ошибкой. Определите этап (`version`, `config`, `auth`, `project`) и при необходимости выполните соответствующую команду локально для просмотра ошибки. Не публикуйте полный debug-log без проверки на секреты.

`GCLOUD_TIMEOUT`: процесс команды превысил лимит 15 секунд. Это лимит одного вызова, а не обещание времени выполнения всей диагностики. На Windows остановка PowerShell по тайм-ауту не является гарантией завершения всех потомков; при зависшем SDK проверьте процессы перед повторным запуском.

`GCLOUD_OUTPUT_LIMIT`: stdout/stderr превысил 1 MiB. `INVALID_JSON` и `INVALID_RESPONSE`: формат ответа не соответствует ожиданиям; не записывайте фиктивную версию или фиктивный статус, чтобы обойти проверку.

`CLI_PROJECT_DIFFERS_FROM_BINDING` — предупреждение, не команда переключить глобальный проект. `NO_LOCAL_CREDENTIALS` и `CONFIGURED_ACCOUNT_NOT_LISTED` не проверяют валидность ADC. Настроенная service-account impersonation отмечается отдельно.

## Как это связано с моделью и задачами GitMir

Для подготовки облачного изменения навык использует фактическую привязку и диагностику, затем передаёт задачу существующему планировщику. Локальные изменения приложения отделяются от удалённых операций. В задачах должны быть указаны ресурс, project ID, необходимые API/IAM-права, возможные расходы, откат и исполняемые проверки `## Verify`.

Сам исполняемый helper **не содержит** команд deploy/delete, IAM, services enable, billing, auth login, print-access-token, config set или components update. Он не принимает произвольные аргументы `gcloud` из файла проекта. Его process adapter допускает только три локальные команды и одно чтение проекта с валидным ID.

Граница helper обеспечивается кодом, а правила поведения Codex — инструкциями навыка. Навык не является технической песочницей для всего Codex: общие разрешения агента по-прежнему определяются его средой выполнения и настройками оператора.

На Windows вызов `gcloud.cmd` идёт через фиксированный PowerShell-скрипт с `-NoProfile`, `-NonInteractive`, `-EncodedCommand` и отдельным quoting аргументов; прямой `execFile` для `.cmd` не применяется. Особенность запуска `.cmd` в Windows описана Node.js.[5] Execution Policy системы не отключается.

## Обслуживание Windows SDK и WinGet

[Рецепт обновления до 584.0.0 и исправления Unknown](windows/gcloud-winget-version-repair/README.md) сохранён отдельно. Он не запускается ни установщиком навыка, ни doctor, ни стартом панели.

Версия **584.0.0** в том рецепте — историческая цель конкретного разбора, а не актуальная минимальная версия этой интеграции. Doctor не требует её установки. Нельзя понижать более свежий SDK ради совпадения с примером. Успешный end-to-end прогон исходного Windows-рецепта на компьютере пользователя ранее не был подтверждён; добавление интеграции этого статуса не меняет.

Принцип обслуживания: сначала проверить реальную версию; при необходимости и по отдельному решению обновить SDK; только затем исправлять metadata `DisplayVersion`. Не путать отсутствующие сведения WinGet с pinning и не записывать неустановленную версию.

## Проверки и границы валидации

```powershell
npm run test:gcloud
```

Тесты используют встроенный `node:test`. Они проверяют локальный режим без удалённых команд, явную привязку, отказ при неверной схеме, фильтрацию секретных полей, ошибки SDK и API, запуск реального дочернего процесса с подставным `gcloud`, пути с пробелами, ссылки/junctions установки, CLI exit codes и совпадение навыка в двух каталогах.

Workflow `.github/workflows/google-cloud-tests.yml` запускает этот набор на Ubuntu, Windows и macOS с Node.js 22.18.0. Наличие workflow само по себе не означает, что конкретный CI-прогон уже зелёный: смотрите Checks у коммита или PR.

Подставной CLI — не реальный Google Cloud SDK. Проверка на настоящем аккаунте, Windows-ремонт и визуальный запуск панели не заявляются выполненными без соответствующего вывода. Полный typecheck существующего приложения относится к отдельному набору проверок; этот модуль не меняет TypeScript backend/frontend.

## Исходники

- `plugin/skills/google-cloud/SKILL.md` — основной навык Codex.
- `skills/google-cloud.md` — идентичная копия для панели, зарегистрированная в `skills.json`.
- `plugin/skills/google-cloud/scripts/doctor.mjs` — привязка, диагностика, отчёт и CLI.
- `plugin/skills/google-cloud/scripts/gcloud.mjs` — ограниченный process adapter.
- `tests/google-cloud.test.mjs` — unit/integration/packaging проверки.
