# GitMir: аудит всего исходного среза средствами Adaptive

Дата: 10 сентября 2026 года. **Вердикт: RED — проверенный срез нельзя считать прошедшим аудит.**

20 исходных тестов Google Cloud проходят на каждой из трёх ОС, но дополнительные проверки фактического поведения выявили **12 разных дефектов GitMir**: 10 в сервере/relay и два разных сценария конфликта установщика. Ошибки проверяющего инструмента и ложное срабатывание сканера в это число не включены. Исправления приложения в рамках этого аудита не выполнялись.

## 2. Что действительно прошло

На каждой ОС прошли установка зависимостей через `npm ci --ignore-scripts`, `npm run typecheck`, проверка синтаксиса всех восьми JS/TS-файлов, трёх shell-файлов и файлов PowerShell штатным парсером. JSON проверялся отдельно; `tsconfig.json` исключён из строгого JSON-парсера, его читает TypeScript. `npm audit --json` сообщил ноль известных уязвимостей зависимостей в момент запуска. Это результат базы зависимостей, а не доказательство безопасности кода приложения.

Реальный HTTP-сервер прошёл проверки выдачи панели и клиентского JavaScript, добавления/переименования/удаления проекта, обнаружения дубликата проекта, обычного создания и чтения задачи, чтения модели и формирования share-export. Все 12 зарегистрированных навыков доступны через API. Обычный запрос с посторонним `Origin` отвергается; preview-host `127.0.0.1` не получает доступ к обычному API.

В реальном relay-модуле с подставным транспортом статус не раскрывает ключ соединения, а явный путь обхода каталогов в имени файла модели отвергается. Чистая и повторная установка навыков проходят на всех ОС. **Эти положительные сценарии не покрывали обнаруженные ниже конфликты, подстановки и повторную доставку.**

Исходные Google Cloud-тесты используют искусственный `gcloud`. Реальные учётные данные, ADC, доступ к облаку и SDK-ремонт этим не подтверждены.

## 3. Двенадцать подтверждённых дефектов

Приоритеты P1/P2 ниже — рекомендация по исправлению, а не вычисленный CVSS. P1 следует закрыть до расширения функциональности и объявления безопасного релиза. Все воспроизведения ограничены фиктивными файлами, одноразовыми каталогами и loopback-сервисами.

### GM-01 · P1 · Windows-установщик удаляет чужой каталог навыка

**Источник:** [install.ps1](https://github.com/Dimkox/gitmir-codex-control/blob/0c9db4635407cb30faab7a3f1887634db097324e/install.ps1). Пробы: `install-pwsh-conflict`, `install-windows-powershell-conflict`.

При существующем обычном каталоге `.agents/skills/google-cloud` установщик выполняет рекурсивное удаление перед созданием junction. Контрольный пользовательский файл исчез в проверках через оба интерпретатора Windows; код завершения — 0. Это подтверждённая потеря данных, а не просто неверное сообщение об установке.

**Приёмка исправления:** не удалять обычные каталоги при конфликте; различать собственную ссылку, чужую ссылку и пользовательский каталог; проверять принадлежность и целевой путь перед заменой. Конфликт должен завершаться понятной ошибкой без потери контрольного файла, а свежая и повторная установки — сохранять работоспособность.

### GM-02 · P1 · Linux: имя каталога исполняется как shell-подстановка

**Источник:** [server.ts](https://github.com/Dimkox/gitmir-codex-control/blob/0c9db4635407cb30faab7a3f1887634db097324e/server.ts), `openInTerminal`. Проба: `linux-terminal-path-is-literal`.

Путь включается в строку для `bash -lc` через `JSON.stringify`. JSON-кавычки не делают строку безопасным литералом shell. Существующий тестовый каталог с подстановкой в имени привёл к созданию безвредного контрольного файла при вызове `/api/open`. Терминальный launcher заменён фикстурой, исполняющей переданные ему аргументы; пользовательский рабочий терминал не использовался.

**Граница доказательства:** подтверждено на Linux. Нужен контролируемый путь проекта; интернет-атака без дополнительных условий не доказывалась. Windows/macOS для этой конкретной ветки помечены SKIP.

**Приёмка:** передавать путь через `cwd`/аргументы без интерполяции shell либо через корректно обработанный позиционный аргумент статической shell-команды. Имена с пробелами, кавычками и метасимволами должны оставаться данными.

### GM-03 · P1 · Host проверяется по префиксу, а не точному имени

**Источник:** `server.ts`, `sameOrigin`. Проба: `http-reject-host-suffix`.

Запрос к `/api/projects` с `Host: localhost.attacker.invalid:<port>` получил HTTP 200 вместо 403 на каждой ОС. Регулярное выражение принимает разрешённый префикс без обязательной границы hostname.

**Граница доказательства:** выполнен прямой HTTP-запрос к loopback. Полная браузерная атака с DNS rebinding не проводилась; положительный тест обычного `Origin` эту дыру не закрывает.

**Приёмка:** разбирать и сравнивать точные hostname/port; отклонять суффиксы, неоднозначные и некорректные формы. Положительные проверки штатных адресов и отрицательные проверки поддельных Host должны выполняться на всех ОС.

### GM-04 · P1 · Preview отдаёт сторонний исполняемый HTML на origin панели

**Источник:** `server.ts`, `/api/preview`. Проба: `preview-untrusted-html-not-on-dashboard-origin`.

Через preview на `Host: localhost` был получен HTML тестового upstream со скриптом, HTTP 200 и без CSP sandbox. Использование отдельного hostname в штатном интерфейсе не заменяет проверку самого HTTP-entrypoint.

**Граница доказательства:** подтверждены тело ответа, content type, hostname и заголовки. Выполнение атакующего кода в браузере реального пользователя не проверялось.

**Приёмка:** не обслуживать untrusted preview на привилегированном origin панели; обеспечить отдельный origin и подходящую sandbox-политику. Прямой запрос в обход UI также должен сохранять изоляцию.

### GM-05 · P1 · IPv4-mapped IPv6 обходит ограничение loopback в proxy

**Источник:** `server.ts`, preview proxy и классификация адресов. Проба: `preview-ipv6-mapped-loopback-is-blocked`.

Маршрут `/api/px` получил контрольный ответ локального upstream через IPv4-mapped IPv6, хотя для этого пути прямой loopback должен быть запрещён. Воспроизведено на всех трёх ОС. Внешние сервисы, LAN и облачные metadata endpoints не запрашивались.

**Приёмка:** нормализовать IP-формы и проверять реально выбранный адрес назначения, включая переходы по redirect. Дополнительно проверить DNS-ответы и смену адреса между проверкой и соединением; эти более широкие сценарии пока являются задачами на проверку, а не доказанными эксплуатациями.

### GM-06 · P1 · Создание задач молча перезаписывает предыдущие задачи

**Источник:** `server.ts`, POST `/api/task`. Проба: `http-task-identities-do-not-collide`.

**12 успешных запросов с одинаковым заголовком дали один уникальный файл** на каждой ОС. Идентификатор на основе времени с точностью до секунды и slug заголовка сталкивается, запись не выполняется с гарантией эксклюзивного создания.

**Приёмка:** независимые уникальные ID и атомарное создание без перезаписи, с корректной обработкой коллизий. Серия и параллельный пакет одинаково названных задач должны сохранять все тела, а не только последний запрос.

### GM-07 · P1 · Входящая модель relay записывается через symlink вне проекта

**Источник:** [relay.ts](https://github.com/Dimkox/gitmir-codex-control/blob/0c9db4635407cb30faab7a3f1887634db097324e/relay.ts), обработчик модели. Проба: `relay-model-write-rejects-symlink`.

Безопасное по строковому имени `entities.json` было заранее заменено ссылкой на контрольный файл вне каталога проекта. Входящий кадр реального обработчика модели перезаписал этот файл на всех ОС. Проверка имени от `../` сработала, но файловая ссылка обходится без `../` в сообщении.

**Условие:** соответствующий symlink должен уже присутствовать в дереве. Произвольная запись на чистой файловой системе без этого условия не доказана. Транспорт подставной, внешний relay не использовался.

**Приёмка:** no-follow/containment-проверки и безопасная атомарная запись, учитывающие ссылки и подмену пути; внешняя контрольная цель должна остаться неизменной.

### GM-08 · P1 · Режим relay «local» отправляет содержимое очереди

**Источник:** `relay.ts`, обработка welcome / отправка очереди. Проба: `relay-local-level-does-not-send-queue`.

После welcome с уровнем `local` реальный модуль отправил в подставной WebSocket содержание тестовой очереди, одновременно показывая обещание, что ничего не покидает компьютер. Воспроизведено на всех ОС.

Это подтверждённое расхождение поведения и пользовательского обещания. Оно не доказывает намеренную утечку, фактическую отправку пользовательских секретов или политику хранения внешнего сервиса: в тесте использовалась только искусственная очередь и fake transport.

**Приёмка:** определить контракт уровня `local` и выполнить его во всех отправителях и watchers. При обещании полного отсутствия передачи ни начальная синхронизация, ни последующие изменения не должны отправлять содержимое очереди.

### GM-09 · P2 · Выполненная задача возвращается в todo при повторной доставке

**Источник:** `relay.ts`, дедупликация входящих задач. Проба: `relay-completed-task-replay-after-fresh-state`.

После первой доставки задача перенесена в `done`. Затем создано свежее состояние модуля и повторно доставлен тот же ID — задача снова появилась в `todo` на каждой ОС. Память процесса и проверка только текущего `todo` не дают устойчивой идемпотентности.

**Граница:** воспроизводилась потеря состояния через новый экземпляр модуля, не реальный перезапуск компьютера и не поведение production-backend.

**Приёмка:** постоянная дедупликация с областью проекта и учётом завершённых/архивных состояний; повторный кадр не должен запускать работу заново.

### GM-10 · P2 · JSON null вызывает внутреннюю ошибку API

**Источник:** `server.ts`, POST `/api/task`. Проба: `http-invalid-json-is-client-error`.

Синтаксически допустимый JSON `null` даёт HTTP 500, а не ошибку валидации 4xx на всех ОС. Объект разбирается без проверки формы входного значения.

**Приёмка:** валидировать тип и поля тела до чтения свойств; `null`, массивы, скаляры и отсутствующие обязательные поля возвращают предсказуемый 4xx без изменения состояния.

### GM-11 · P2 · Обычный файл принимается за каталог проекта

**Источник:** `server.ts`, `/api/add`. Проба: `http-add-rejects-regular-file`.

Существующий текстовый файл зарегистрирован как проект с `added: true` на всех ОС. Проверки существования недостаточно для проверки каталога.

**Приёмка:** проверять тип файлового объекта и выбранную политику разрешения ссылок. Обычный файл не должен попадать в список проектов, а валидный каталог с пробелами — должен.

### GM-12 · P2 · POSIX-установщик сообщает успех при конфликте реального каталога

**Источник:** [install.sh](https://github.com/Dimkox/gitmir-codex-control/blob/0c9db4635407cb30faab7a3f1887634db097324e/install.sh). Проба: `install-bash-conflict`.

При существующем обычном каталоге навыка установщик завершился кодом 0 на Ubuntu и macOS, но ожидаемый `SKILL.md` непосредственно в месте установки отсутствовал. `ln -sfn` не реализует требуемую безопасную замену обычного каталога.

**В отличие от Windows, контрольный пользовательский файл сохранился.** Дефект здесь — неверная структура/ложный успех, а не доказанное удаление данных.

**Приёмка:** явно отвергать конфликт с чужим обычным каталогом и проверять результирующую ссылку перед успешным завершением, не повреждая пользовательские данные.

## 4. Что выявлено у проверяющего инструмента и его окружения

### Неоднозначная база PR на Ubuntu/macOS

Неизменённый `grok_verify.py --mode pr --no-record --json` вернул `pr-base-ambiguous`: checkout содержит разные `origin/main` и `origin/master`, но не имеет однозначного `origin/HEAD`. Это отказ выбора базы проверки, **не самостоятельный дефект runtime GitMir**.

Известная основная ветка проверяемого репозитория — `master`. Для следующего воспроизводимого PR-прогона следует явно подготовить эту локальную ссылку в одноразовом checkout. Нельзя удалять ветку `main` на сервере или придумывать route/approval, чтобы скрыть проблему. Первичный результат и журнал сохранены без такой нормализации.

### Windows: preflight обрывается на POSIX API

На Windows фабричный verifier не сформировал JSON-отчёт: `architecture_diff._stop_process` вызвал отсутствующий `os.killpg`. Это проблема переносимости проверяющего движка. Проверки TypeScript, Google Cloud и собственные HTTP/relay-пробы при этом завершились отдельно и имеют самостоятельные результаты.

Планировщик установки фабрики на Windows также отказал с `UnsafeInstallTarget: safe no-follow directory operations are unavailable`. Это fail-closed ограничение файловых примитивов; нельзя заменять его небезопасным следованием ссылкам ради совместимости. Нужен поддерживаемый Windows-backend либо явное документирование POSIX/WSL-границы. На Ubuntu/macOS `--plan` завершился успешно.

### Сканер секретов: reviewed false positive

Сканеры фабрики отдельно получили **все 81 отслеживаемых файла**, а не только diff. `generic-secret` отметил [tests/google-cloud.test.mjs](https://github.com/Dimkox/gitmir-codex-control/blob/0c9db4635407cb30faab7a3f1887634db097324e/tests/google-cloud.test.mjs). В прочитанном файле находятся искусственные значения для проверки удаления секретных полей из отчёта: `SECRET-PROXY`, `SECRET-TOKEN`, `SECRET-REFRESH`.

Это тестовая фикстура, **не подтверждённый действующий токен**. Не следует удалять тест приватности или глобально отключать secret scan ради зелёного статуса. Нужна узкая, проверяемая обработка искусственных фикстур при сохранении обнаружения настоящих секретов.

### Пропущенные контракты — не пройденные контракты

Архитектура и governance в проверяемом GitMir не настроены для этого движка и получили SKIP. Сканеры сообщили 0 проверенных контрактов и 0 SQL-находок: это не доказательство корректности HTTP-контрактов или несуществующей здесь схемы БД. Независимых agent-review receipts и deployed Trust CI attestation нет.

## 5. Дополнительные направления ревью — пока не динамические находки

При чтении исходников требуют отдельной проверки лимиты HTTP request body, прекращение чтения preview-response до накопления полного тела, DNS/redirect-ограничения proxy, чтение ссылок при исходящей синхронизации модели и ограничения relay-кадра до JSON-декодирования. Эти пункты не включены в 12 подтверждённых дефектов.

Windows-рецепт SDK по-прежнему является отдельной ручной процедурой с фиксированной версией и оговорёнными ограничениями. В этом прогоне проверен его синтаксис, **не** обновление SDK, сопоставление установленного `gcloud` с записью реестра или исчезновение `Unknown`.

Старый Webpack-workflow не исправлялся и не является критерием успешности данного аудита. Результат `typecheck` не называется результатом Webpack-сборки.

Параметр `--target` **не должен указывать на рабочую пользовательскую установку**: сервер создаёт служебное состояние, тесты устанавливают навыки в временный HOME и создают/удаляют контрольные файлы. Пробы дефектов намеренно завершаются ненулевым кодом на исходном срезе.

Нужны Git, Node.js 22.18.0, npm, Python 3.12; для полного набора синтаксических проверок — Bash и PowerShell. Отсутствующий интерпретатор фиксируется отдельно, а не считается успешной проверкой.

```text
git clone https://github.com/Dimkox/gitmir-codex-control.git audit-driver
git -C audit-driver checkout --detach 69fa4934f0f41d46acc23bb5d75261e956aa53d9
git clone https://github.com/Dimkox/gitmir-codex-control.git target

git clone https://github.com/Dimkox/adaptive-grok-build-pro.git framework

```

Обычный `git clone` может подготовить `origin/HEAD` иначе, чем `actions/checkout` в зафиксированном запуске. Поэтому повторение `pr-base-ambiguous` зависит от локальных refs; это не причина игнорировать воспроизводимые HTTP, relay и installer-дефекты.

Ветка `audit/adaptive-full-project-20260910` продвинулась параллельно подготовке этого прогона. Её коммиты сохранены, force push не выполнялся. Этот отчёт относится к самостоятельному запуску ветки `audit/adaptive-runtime-addendum-20260910`, а не приписывает себе результаты другого драйвера.

## 8. Решение по выпуску и границы уверенности

Рекомендация — сначала закрыть потерю данных установщиком и очередью, shell-интерполяцию, Host/preview/proxy-изоляцию, запись через ссылки и несоответствие режима `local`; затем исправить replay и валидацию. Каждый фикс должен переводить соответствующую негативную пробу в PASS без ослабления ожиданий, после чего нужен новый полный трёхплатформенный прогон.

Проверка охватила исходный срез всего репозитория, но не все возможные сценарии эксплуатации. Не проверены реальная модельная задача Codex, интерактивные действия в GUI/выборщике каталога, полный browser E2E, реальный Google Cloud/ADC/биллинг, production relay, SDK/registry repair и deployed Trust CI. Проверенные runner-платформы также не означают поддержку всех Windows desktop, Intel Mac и Linux-дистрибутивов.

**В этой публикации нет исправления приложения, merge, релиза или изменения production-инфраструктуры. Отрицательный результат сохранён как отрицательный.**
